02 - TECH STACK (DECIDED)
==========================

All decisions below are final for v1. Do not revisit unless a specific
implementation blocker forces a change.


FRONTEND
---------
Technology: Next.js
Hosting:    Vercel (free tier)
Why:        React-based, easy deployment, no config needed


API BACKEND
------------
Technology: FastAPI (Python)
Hosting:    Render.com (free tier, spins down when idle — acceptable for MVP)
Why:        Same language as the worker. One language = one deployment unit.
            FastAPI auto-generates API docs at /docs just by running.
            Handles async file uploads natively.

NOT Spring Boot. That decision is dropped. Reason: Spring Boot is Java.
The worker is Python. Running both languages increases complexity and cost.


PYTHON WORKER
--------------
Technology: Python (same Render service as FastAPI at MVP scale)
Why:        No separate deployment needed until there's a reason to split.
            The API receives the upload and queues the job.
            The worker polls the queue and processes it.
            Both live in one service at this scale.


DATABASE
---------
Technology: Supabase (hosted Postgres)
Cost:       Free tier — 500MB storage, plenty for this volume
Why:        Managed Postgres. No server to run. Python client available.
            The jobs table doubles as the queue (no separate queue service).


VIDEO STORAGE
--------------
Technology: Cloudflare R2
Cost:       Free up to 10GB. No egress fees (unlike AWS S3).
Why:        S3-compatible API — use boto3 in Python with a small config change.
            No per-download charges is important since videos are large files.


QUEUE
------
Technology: Postgres jobs table (polling — no separate service)
Why:        SQS, RabbitMQ, and Redis add operational overhead with no benefit
            at this scale (one video at a time).

How it works:
  - analysis_jobs table has a status column: queued / processing / done / failed
  - Worker polls every 5 seconds:
      SELECT * FROM analysis_jobs WHERE status = 'queued' LIMIT 1
  - When a job is found, worker claims it and processes the video
  - When done, worker writes results and marks job as 'done'

This is called a polling queue. It is a valid production pattern at low volume.
When multi-video concurrency is needed, swap in SQS — the rest of the code
does not change because the queue interface is behind a function call.


AI / CV LIBRARIES
------------------

Object Detection: YOLOv8 Nano (YOLOv8n)
  - Library: ultralytics (pip install ultralytics)
  - Model file: yolov8n.pt (~6MB, downloads automatically)
  - Detects: "person" and "sports ball" from COCO dataset — no training needed
  - Runs on CPU (no GPU required for MVP)
  - Throughput: ~5-15 frames/second on CPU
    → 10-minute video at 30fps = 18,000 frames = 20-60 min processing on CPU
    → Acceptable for a background job demo

Player Tracking: ByteTrack
  - Library: supervision (pip install supervision)
  - What it does: takes YOLO detections frame-by-frame and assigns stable
    integer track IDs across the entire video
  - Handles occlusion via Kalman filter (predicts position when player hidden)
  - Result: Track 1-6 stay consistent for the whole video

Ball Tracking: Same YOLO + ByteTrack pipeline
  - Uses the "sports ball" detection class
  - ByteTrack handles ball disappearing mid-flight

Jersey Color Classification: OpenCV K-means
  - Library: opencv-python (pip install opencv-python)
  - Process:
      1. Crop the middle third of each player bounding box (jersey area)
      2. Find dominant color of that region using K-means (k=1)
      3. After sampling all 6 players, cluster into 2 groups (k=2)
      4. Assign team label A or B to each cluster
  - Requires no training data, no OCR, runs instantly

Hoop Detection: Two options
  - Option A: Fine-tune YOLOv8n on a small labeled hoop dataset (Google Colab)
  - Option B (MVP fallback): Detect hoop position once in the first few frames
    using Hough Circle Transform (OpenCV), then treat it as fixed for the video.
    Works because the hoop does not move.


MONTHLY COST AT MVP SCALE
---------------------------

  Frontend (Vercel)       $0
  Backend (Render)        $0
  Database (Supabase)     $0
  Video Storage (R2)      $0 (under 10GB)
  Queue (Postgres table)  $0
  AI models (open source) $0
  -------------------------
  Total:                  $0

Future cost trigger: GPU compute. A GPU instance (e.g. AWS EC2 g4dn spot)
brings processing from 20-60 min down to under 2 minutes. Only needed when
there are paying users requiring fast turnaround.
