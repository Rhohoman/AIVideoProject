MVP Main Flow


User uploads video
   ->
Backend stores video
   ->
Video processing service extracts frames
   ->
Computer vision models detect:
   - players
   - jersey numbers/colors
   - ball
   - hoop/court
   ->
Tracking service keeps identity of players across frames
   ->
Action recognition service labels events:
   - dribble
   - shot
   - pass
   - rebound
   ->
Stats engine converts events into basketball stats
   ->
Results saved to database
   ->
Frontend shows report and timeline

REALISTIC LIMITATIONS



This kind of system is hard. It helps to be honest about what the MVP can and cannot do.

Hard problems
Occlusion

Players block each other.

Motion blur

Fast movement makes jersey numbers hard to read.

Camera angle changes

Broadcast cameras zoom and pan.

Similar uniforms

Multiple players wear same jersey color.

Small ball size

Basketball is hard to track consistently.

Official stat accuracy

High accuracy for assists, steals, and blocks is much harder than simple shot detection.

Because of that, your MVP should not promise full official stat replacement.

A better promise is:

AI-assisted player tracking and event estimation for basketball videos.

That wording is safer and more realistic.

Best MVP scope


*********
One practical note

For your first implementation, you may not even need separate microservices deployed independently yet.

You could start with:

one frontend app
one Spring Boot backend
one Python worker
one Postgres database
one object storage bucket
one queue

That is still a good architecture.
It is not “too simple.” It is the right amount of simple.
*********

I would narrow the MVP to this:

MVP v1

Input:

one uploaded basketball video
user specifies jersey number and jersey color

System does:

detect all players
identify likely target player
track target player through video
detect possession periods
detect shot attempts
detect made shots
estimate points
output event timeline

Frontend shows:

player summary
timestamps of shots
estimated points
confidence scores
MVP v2

Add:

rebounds
passes
shot chart
heatmap
simple highlight clip generation
MVP v3

Add:

assists
steals
team-level stats
multi-player tracking in one run
brand/logo detection

This staged approach matters because the full system is big.

That is a very smart future feature because it opens another business use case.

Service design




How the processing can be broken into services

If you want deeper system design language, here is how to think about service boundaries.

Service 1: Video ingestion service

Responsibility:

accept upload
validate format
save file
create job
Service 2: Frame extraction service

Responsibility:

read video
extract frames
save frame data
Service 3: Detection service

Responsibility:

detect players, ball, hoop, logos
Service 4: Tracking service

Responsibility:

assign persistent identities across frames
Service 5: Event inference service

Responsibility:

convert motion/positions into basketball events
Service 6: Stats service

Responsibility:

convert events into final player stats
Service 7: Results API

Responsibility:

present processed results to frontend

For MVP, some of these can live in one Python worker.
Later, they can be separated if scale increases.

That is an important design idea:

Monolith first, services later

At the beginning, keep the processing pipeline inside one service.
Only split it into microservices when scale or complexity demands it.

That is usually the right answer for a first product
